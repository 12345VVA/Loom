## 二、方法论：「本地绿 CI 红」的排查序

按差异面出现频率排序，逐层排除：

1. **依赖版本漂移**（本次两轮红的根因）——本地 venv 版本组合与 CI 全新安装永远不同步
2. **配置基线差异**——本地 `.env` ≠ CI 的 `.env.example` + job 级 env 覆盖
3. **方言差异**——SQLite（开发）vs PostgreSQL（CI/生产），本地用 PG schema 跑全量即可排除
4. **runner 环境残余**——Linux/UTC/资源差异，本地无法模拟，只能拿日志

**两条原则**：

- **复现优于猜测**。拿不到日志就造等价环境：
  - *PG schema 演练法*：读 `.env` 的 `SQL_*` 字段拼连接串，追加 `?options=-csearch_path%3D<schema>`（密码含特殊字符用 `urllib.parse.quote`），先 `DROP SCHEMA ... CASCADE` 再 `CREATE SCHEMA` 模拟 CI 空库，跑完 `DROP` 清理。无 CREATEDB 权限也能完整复现 CI 数据库场景
  - *env 基线注入法*：把 `.env.example` 全部键值注入 `os.environ` 再叠加 job 级覆盖（pydantic-settings 环境变量优先于 env 文件），等价 CI 配置。第 6 轮的 4 个红点就是这么在本地原样复现的——本地 `.env` 永远复现不了
- **工具链先行**。仓库公开时 GitHub API 匿名可读 runs/jobs/steps/annotations（日志下载 403）；gh CLI 装好认证后日志自助拉取：`gh run view <id> -R <repo> --job <id> --log`。**这个应该 CI 首跑前就装好**，前三轮的贴日志沟通全是学费。

## 三、工程教训（已制度化）

| 教训 | 制度 |
|---|---|
| `>=` 下限无上界 + 无 lock = 时间炸弹 | `requirements.lock` constraints 模式：`requirements*.txt` 保持语义化下限，CI 安装 `-c requirements.lock` 钉整树。**升级依赖的标准流程**：本地装新版 → 全量 pytest → 重新 freeze 更新 lock → push |
| 测试依赖环境默认值 | 测试内 `patch.object(settings, ...)` 显式锚定前提，不赌 conftest / `.env.example` / config 默认三者一致。`.env.example` 与 config 默认会漂移，需在 example 变更时对照 config |
| 跨层配置"设计意图"打架 | CI job env 优先级 > conftest 的 `setdefault`——job env 一旦覆盖，conftest 声明的测试前提失效。跨层配置要有单一权威，禁止项在 workflow 里注释说明 |
| Celery 惰性注册 | 独立脚本读 `celery_app.tasks` 前必须 `celery_app.loader.import_default_modules()`（`include` 模块由 worker 启动时才 import） |
| 门禁的价值实证 | celery 校验首次真正执行即抓到真实配置缺陷；alembic check 首跑抓到 10 处索引 drift。**被前面门禁挡住的步骤首跑必红**——流水线每变绿一层就暴露下一层欠账，排障预算按"洋葱层"估，不按"一个 bug"估 |

**伪失败陷阱**：`main.py` lifespan 启动检查失败会 `sys.exit(1)`——本地复现时若把 `DATABASE_URL` 指向死地址，所有 TestClient 用例全挂，且堆栈被淹在中间件链里，容易误判为业务问题。

## 四、技术债清单（本次未解，后续专项）

1. **sqlmodel 解禁**（钉 `0.0.38` 的还债工程）：
   - `BaseEntity` 等 `default_factory=datetime.utcnow`（naive）→ `datetime.now(UTC)`（aware）
   - 列类型 `timestamp` → `timestamptz`：alembic 迁移 + PG 存量数据标准化，否则 `alembic check` 报 drift、新旧值混比 TypeError
   - 清查业务代码与测试里的 naive datetime 构造；SQLite/PG 读回行为差异回归
2. **迁移链不支持从零部署**：baseline 0001 为空壳版本戳（表由应用 `create_all` 建表），CI 按真实部署路径验证（init_db+stamp+check）。长期要么补全 baseline 要么文档化"迁移仅作增量记录"
3. **CI 设计文档后续阶段**：Step 2 测试参数化收编（make_test_engine）、Step 3 SQLite 代码退场
