# Loom 生产部署演练实录（2026-10-04）

> 对应：治理方案 G6 / 评审 H3「生产部署故事未验证」。
> 环境：Windows 11 + Docker 29.6.2 + Compose v5.3.1，本机 8000 被开发态 uvicorn 占用。
> 结论：**演练通过**。生产栈六容器全 healthy，冒烟五步全绿（health → SPA → 验证码 → 登录 → 鉴权接口）。
> 演练共揪出 **10 个真实问题**（其中 3 个是"修好了也会被 merge 语义静默吃掉"的深坑）——
> 印证评审判断：生产镜像此前从未被真正消费过。

## 一、交付物

| 文件 | 内容 |
|---|---|
| [docker-compose.prod.yml](../docker-compose.prod.yml) | **独立全量 spec**（非 override，原因见问题 #1）；安全基线：pg/redis/backend 不发布端口、Redis requirepass、专用命名卷、restart 策略、celery 专用探针 |
| [.env.prod.example](../.env.prod.example) | backend Settings **全量**生产模板（字段与 backend/.env.example 对齐；缺必填字段容器起不来——问题 #5 实测） |
| [frontend/Dockerfile](../frontend/Dockerfile) | `npm ci`（吃 lock，可复现）+ `ARG NPM_REGISTRY` 可配 |
| [frontend/nginx.conf](../frontend/nginx.conf) | upstream 改 `backend:8000`（原 `midway:8001` 为 cool-admin 遗留、必然 502）；补 `/uploads/` 透传（产物图片引用路径） |
| [scripts/deploy_smoke.sh](../scripts/deploy_smoke.sh) | 可复用冒烟：health → SPA → 验证码 → 登录 → 鉴权，全走 nginx 真实链路 |
| [.gitignore](../.gitignore) | 补 `.env.prod`（原 `*.env` 规则盖不住该后缀，密钥有裸奔入库风险） |

## 二、启动方式

```bash
cp .env.prod.example .env.prod   # 改掉全部密钥/口令（openssl rand -hex 32）
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
bash scripts/deploy_smoke.sh     # 传 BASE_URL/ADMIN_USER/ADMIN_PASS/REDIS_PASSWORD
```

## 三、演练揪出的问题（按发现顺序）

| # | 问题 | 根因 | 处置 |
|---|---|---|---|
| 1 | **override 继承陷阱**：backend"healthy"但实际仍挂 dev 源码卷运行 | compose 对 volumes/ports 按 target **合并**而非替换，`!reset` 在本版本对 volumes 未生效；env_file 列表也是**合并**——"去 dev 挂载/去 dev env"的意图静默失效 | prod 文件改为**独立全量 spec**，零继承 |
| 2 | frontend 容器 exit 127 循环重启 | 继承了 base 的 `command: npm run dev`，nginx 镜像无 npm | 独立 spec 显式用镜像默认 CMD |
| 3 | beat 容器循环重启：Settings 缺必填字段（PORT/OPENAI_BASE_URL/JWT_ALGORITHM…） | override 形态下 beat 只有精简 env 模板 | 模板补全为与 backend/.env.example 对齐的全量字段 |
| 4 | `.env.prod` 不被 `.gitignore` 覆盖 | `*.env` 匹配不了 `.env.prod` 后缀 | 显式 ignore 条目 |
| 5 | Redis healthcheck 失败 | requirepass 后裸 `ping` 返回 NOAUTH | healthcheck 带密码（compose 插值注入） |
| 6 | **prod/dev 命名卷共用**：新 PG 口令认证失败 | 项目名同为 loom → 复用 dev 的 `loom_postgres_data`（集群密码是旧的，`POSTGRES_PASSWORD` 只在空卷首启生效）；dev 数据库存在被误操作的事故面 | prod 专用卷 `loom-prod-*-data` + 容器名 `loom-prod-*` 前缀，与 dev 栈彻底隔离 |
| 7 | 生产强制滑块验证码挡住脚本登录 | `captcha_enabled` 属性：DEBUG=false 强制启用，忽略 .env（这是**正确的安全行为**） | 冒烟从 Redis 侧读取本次 target_x 构造合规轨迹（±12px/时长/轨迹点/回滑全达标）——冒烟是带基础设施凭据的部署验证，非渗透测试 |
| 8 | celery worker/beat 永远 unhealthy | 镜像内置 HEALTHCHECK 打 uvicorn /health，对 worker/beat 无意义 | 覆盖为 celery 探针：worker `inspect ping -d celery@$HOSTNAME`，beat 查 PID1 cmdline |
| 9 | `/uploads/` 无 nginx location | 产物图片以 `/uploads/...` 入库引用，原配置只有 `/api/` | 补透传（演练实测：后端 401 响应而非 nginx 404，链路正确） |
| 10 | 生产镜像不可复现 | `npm install` 绕过 package-lock（评审 H3 原发现） | `npm ci` + registry ARG 化 |

## 四、验证结果

```
loom-prod-backend: Up (healthy)    # 空卷 → alembic upgrade head（baseline squash 从零部署）→ startup 硬门禁（DEBUG=false）全过
loom-prod-worker:  Up (healthy)    # celery inspect ping 探针
loom-prod-beat:    Up (healthy)    # beat_schedule 定时任务有人调度
loom-prod-pg:      Up (healthy)    # 专用卷全新初始化
loom-prod-redis:   Up (healthy)    # requirepass + 带密码探针
loom-prod-web:     Up              # nginx 静态 + /api /uploads 反代

冒烟（scripts/deploy_smoke.sh）：
  OK /api/health → healthy          （nginx 剥前缀 + 响应包装解析）
  OK / → SPA index                  （静态资源 + history 路由兜底）
  OK captcha → target_x 基础设施侧读取
  OK login → token 已签发           （滑块验证码 + CSRF Origin 校验下真实登录）
  OK /admin/base/comm/person → 鉴权链路通
```

## 五、遗留与说明

- 演练栈用后即拆（`docker compose --env-file .env.prod -f docker-compose.prod.yml down`）；
  `loom-prod-*-data` 三卷为演练数据，可 `docker volume rm` 清理；`.env.prod` 已 gitignore，留存供下次演练。
- 迁移顺序：backend 容器启动命令内置 `alembic upgrade head`；多副本扩容时需改为独立迁移 Job（当前单副本无此需求）。
- TLS 终结不在本轮范围（部署面通常由云 LB/ingress 承担）；nginx 侧预留标准 443 server 块即可扩展。
