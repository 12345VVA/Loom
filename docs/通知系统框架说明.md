# 通知系统框架说明

Loom 通知系统第一版以站内通知为核心，覆盖系统通知、业务通知和任务通知。通知统一落库，不直接接入 WebSocket、邮件、短信或 Webhook；后续可在服务层扩展投递 provider。

## 核心模型

- `notification_message`：通知主体，包含标题、内容、类型、级别、来源模块、业务键、跳转链接、发送状态、计划发送时间和过期时间。
- `notification_recipient`：用户接收记录，包含用户、部门、已读、归档状态。字段 `role_id` / `tenant_id` / `is_deleted` 为**预留字段，当前无写入路径**（软删除以 `notification_message.delete_time` 为准）。
- `notification_template`：通知模板，支持标题模板、内容模板、默认级别和默认跳转链接。占位符仅支持**简单变量名**（如 `{taskName}`）；自动编号 `{}`、嵌套格式说明符 `{a:{w}}`、属性/下标访问一律拒绝（400）。
- `notification_rule`：受众规则表。**当前未接线**——发送链路只接受内联 `AudienceRule`，不存在按 `code` 加载该表的通路；表/接口/页面仅供 CRUD，对实际投递无影响（见「当前边界」）。

> **预留未实现**：`notification_message.scheduled_at`（计划发送时间）与 `send_status` 字段**无任何调度器/消费者**，当前不会真正定时发送；写入即 `sent`，从不更新。

## 服务入口

`NotificationService` 提供统一发送能力：

```python
NotificationService(session).send_system(...)        # 系统通知（默认受众 = 全体管理员）
NotificationService(session).send_business(...)      # 业务通知
NotificationService(session).send_task(...)          # 任务通知（可按模板渲染）
NotificationService(session).send(...)               # 管理端手动发送，返回投递结果（含收件人数）
NotificationService(session).render_template(code, context)
NotificationService(session).preview_template(code, context)
NotificationService(session).resolve_recipients(rule)
NotificationService(session).preview_recipients(rule)
```

受众规则可传 `AudienceRule`、`dict` 或 JSON 字符串。系统会解析用户、角色、部门和全体管理员，并按用户去重。

**投递语义（重要）**：

- **原子投递**：消息与收件人在**同一事务**内写入，任一步失败整体回滚，不会产生「0 收件人的孤儿消息」。
- **空受众拒绝**：受众解析为空（无任何有效接收人）时返回 400，不会静默「发送成功」。
- 畸形受众 JSON / 非法受众字段返回 400，不会抛 500。

## 管理端接口

管理端（`scope=admin`，均需对应 permission）：

- 通用 CRUD：`/admin/notification/message/page|list|info|add|update|delete`
- `/admin/notification/message/send`：手动发送（请求体 `NotificationMessageSendRequest`），响应额外带 `recipientCount`（实际投递人数）
- `/admin/notification/message/previewRecipients`：预览接收人（返回 `count` + 前 20 条样例）
- `/admin/notification/message/stats`：全局统计
- `/admin/notification/message/recipients`：按消息查询接收人明细
- `/admin/notification/message/recall`：撤回（**仅发送者本人或超级管理员**可撤回）
- `/admin/notification/message/myInfo`：当前用户通知详情
- `/admin/notification/message/mine`：当前用户通知列表
- `/admin/notification/message/unreadCount`：当前用户未读数
- `/admin/notification/message/read` / `readAll`：标记已读 / 全部已读
- `/admin/notification/message/archive` / `unarchive`：归档 / 取消归档
- 模板：`/admin/notification/template/page|list|info|add|update|delete`、`/preview`
- 规则：`/admin/notification/rule/page|list|info|add|update|delete`

**读取接口口径**（`mine` / `myInfo` / `unreadCount`）三者一致：均排除**已召回**、**已软删除**、**已过期**的通知。

**批量操作上限**：`read` / `archive` / `unarchive` 单次 `ids` 不超过 200。

## 权限与角色

- `role_codes` 装饰器字段**仅写入 EPS/初始化元数据，运行期不强制**；运行期只校验 `permission`。
- 「我的通知」6 个 permission（`mine` / `myInfo` / `unreadCount` / `read` / `readAll` / `archive` / `unarchive` / `recall` 等）登记在 `backend/app/modules/base/menu.json`。
- 当前**仅 `admin` 与 `task_operator` 两个角色**被授予用户侧通知权限。

> **维护提示**：新增一个能收到/查看通知的角色，需要同步改 3 处——① `notification/menu.json` 管理端权限的 `role_codes`；② `base/menu.json` 用户侧 6 个 permission 的 `role_codes`；③ 控制器 `@Get/@Post` 的 `role_codes`（仅 EPS 元数据，写错不会拦请求，但影响菜单/权限初始化）。

## 任务通知

`TaskInfo` 增加通知配置：

- `notify_enabled`
- `notify_on_success`
- `notify_on_failure`
- `notify_on_timeout`
- `notify_recipients`
- `notify_template_code`
- `notify_timeout_ms`

任务执行完成后，系统根据任务配置判断是否发送通知。耗时任务以 `consume_time >= notify_timeout_ms` 判定超时通知，不改变任务成功/失败状态。

通知发送为 **best-effort 副作用**：模板缺失、受众非法等异常只记 warning，**不会**导致任务被标记为运行失败。

## 当前边界

- 第一版只做站内通知落库；无邮件 / 短信 / Webhook / 企业微信出口。
- `condition` 只支持框架白名单枚举（`active_admins` / `super_admins`），不执行任意表达式。
- `all_admins` 当前实现为「**启用状态的超级管理员**」，与前端标签「全体管理员」不完全一致；`super_admins` 不额外过滤启用状态。二者语义待产品定调。
- 租户受众字段已预留；如果项目未启用完整租户机制，暂不解析租户用户。
- 用户侧列表（`mine`）当前**无分页**，全量返回后在 Python 侧过滤归档。
- 顶栏未读角标通过 `unreadCount` **轮询**（60s）；平台已有 Redis SSE 基建但通知尚未接入。
- `notification_rule` 规则表与 `scheduled_at` 定时发送均**未接线**，见「核心模型」。
