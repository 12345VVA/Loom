## 总评

**架构成熟度 8/10，治理成熟度 6/10。** 这是一个"技术判断力很强、制度闭环没走完"的项目。经过 9 月底至 10 月初的冲刺，CI、架构守卫、迁移校验、安全启动检查四类门禁已真实落地且经受了实战磨合（9 轮 CI 排障有实录）；但**发布管理（tag/CHANGELOG）、供应链安全（依赖扫描）、生产部署验证、本地执行层（pre-commit）四层仍是零**，且暴露出一个反复出现的模式——**治理动作的"最后一公里"习惯性缺失**（守卫脚本用完即弃、e2e 用例写了不提交、评审文档勾选框不更新、AI 指南落后于代码）。

## 二、架构评审

### 2.1 后端——纪律性真实存在

**强项（有守卫背书）**：

- 六道架构守卫构成闭环：metadata 全表校验、core 禁 modules（静态 + 延迟 import 双冻结）、framework 反向依赖全 AST 冻结（`backend/tests/test_arch_guard.py:25` 空集 + 双向对账，stale 条目也报错）、Tarjan SCC 循环依赖全禁、子进程裸 import 验证框架独立性。
- 39 个 controller 全部 `@CoolController`，modules 层手写 APIRouter 为 **0**；权限/菜单/中间件由 `ModuleConfig` 声明式收口。
- 巨石拆分手法标准（门面 re-export，28 个引用方零改动）。
- 测试卫生极好：**0 处 TODO/FIXME**；conftest 每项环境关闭都带事故根因注释；live 外呼测试是"默认全绿"唯一例外且 CI 显式排除。
- DI 注册表（`app/framework/runtime.py` 63 行）干净解开 framework→modules，未注册依赖显式抛错，唯一装配点在 `main.py`。

**问题**：

- **H4【高】workflow ↔ workflow_eval 双向领域耦合，靠 lazy import 逃逸守卫**。eval 侧静态 import workflow（`workflow_eval/service/eval_run_service.py:17`，并跨模块引私有符号 `_async_execute`）；workflow 侧 lazy 反指 eval（`workflow/service/cleanup_service.py:141`、`llm_judge.py:126`）。SCC 守卫只扫顶层 AST，守卫注释自认盲区——**守卫体系目前唯一成建制的逃逸通道**。
- **M9【中】core 与 framework 包级双向**：`core/database.py:14` 依赖 framework 的 BaseEntity，framework 有 13 处反向 import core。"框架独立"只在 modules 方向成立。
- **M6【中】B4 残量 5 个 >800 行文件**：auth_service 1111（登录+验证码+会话+bootstrap 多职责）、controller_meta 930（`_register_crud_routes` 单函数约 338 行）、runtime_service 879（`_stream_invoke` 约 260 行）、media_service 875、workflow_service 807。
- **M7【中】迁移双轨已两次实际漂移**：baseline squash 漏 2 表（0002 补）、真库索引/类型漂移（0019 修）；`alembic check` 只在 CI，tests/ 中 0 处 alembic 引用。
- **L1-L2【低】** 后端无 mypy，ruff 仅 6 规则组 + 5 条全局 ignore；126 处 broad `except Exception` 无分级策略。

### 2.2 前端——EPS 闭环是真闭环，模块层是散的

**强项**：

- `frontend/build/cool/eps.d.ts`（5907 行）经 .gitignore 白名单入库作 CI 基线；B3 后 service 返回 82 个具名 Response 接口；生成链规则、缓存降级根因、dev server 覆盖陷阱全部写进 `frontend/.cursor/rules/eps-dts-generation.mdc`。
- 类型债显性化路线正确：no-explicit-any=error + 841 条豁免计数台账（增减必须 lockstep，unused suppression 也报错）+ `tsconfig.cool.json` 严格试点进 CI 且实测全绿。
- workflow editor 拆分是真拆分：script 仅约 488 行，17 个 composable 配 19 个单测文件，全仓测试最密区域。
- cool 核心层小而硬化（token 刷新请求队列、动态加载失败 10s 熔断、X-Device-Id 聚合头）。

**问题**：

- **M8【中】9 个模块 7 种目录形态**：task 模块缺 config.ts/index.ts——`src/cool/bootstrap/module.ts` 的 glob 扫描注册不了它；media/notification 缺 index.ts；store 仅 base/dict 有、service 仅 ai 有。新模块无单一可抄骨架。
- **M10【中】packages/crud 是"入库但死"的 vendored 副本**：125 个文件在 git 里，但应用实际加载 node_modules 的 registry 版（`src/plugins/crud/config.ts:9`），`/~` alias 全仓唯一引用是被注释的那行——对它的修改不生效，只等漂移。vite-plugin 那份有同步流程且当前 md5 一致，crud 这份连流程都没有。
- **M6（前端侧）【中】巨型组件回积**：log-drawer 1077 行、artifact-drawer 931 行、image-generator-panel 814 行、task/list.vue 730 行（且完全绕开 cl-crud 手写）。B4 只拆了 editor，标准未外溢。
- **L5【低】** `tsconfig.json:8` 全局 `noImplicitAny: false` 未收回，严格只覆盖 5 个目录子集；eps.d.ts 自身 259 处 any 在 lint 视野外。

## 四、主题性观察

1. **"最后一公里"是当前最系统的弱点**：守卫脚本用完即弃不入库（`scripts/verify_arch_cycle_20261002.py` 未跟踪且 `main()` 无条件 `return 0`）、e2e 用例写了不提交、治理文档勾选框不更新、AI 指南落后于代码。每次治理动作都完成 95%，剩下 5% 系统性流失——它消耗的是治理体系自身的公信力。
2. **守卫强但有已知盲区**：lazy import 逃逸 SCC、EPS 无漂移校验、alembic check 不进本地测试。守卫严格度是"顶层静态"级别，越过这层的耦合（workflow↔eval 正是这么做的）不被拦截。
3. **生产形态是从未被演练的纸面故事**：所有验证都在开发态完成。生产镜像的 lock 绕过 + nginx 假 upstream 说明它一次都没跑通过。
