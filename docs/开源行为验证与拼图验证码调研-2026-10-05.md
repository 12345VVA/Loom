# 开源「行为验证 / 拼图验证码」方案调研（2026-10-05）

> 调研目的：为 Loom 登录链路验证码选型提供依据。
> 背景约束：Loom 自研滑块已被 UI 级实测证明「缺口为确定性变换 → 最朴素图像算法 36/36 精确解出」（见 `docs/登录链路验证码专项分析-2026-10-05.md` §13）。本次调研要回答的是：**GitHub 上有没有现成的开源行为验证 / 拼图验证码项目可用，以及它们能否解决上述短板。**
> 数据口径：star / 协议 / 最近更新均为 **GitHub API 实时抓取（2026-10-05）** 的快照；功能描述来自各项目 README / 官方文档。star 数会随时间漂移，引用时以仓库现状为准。

---

## 0. 结论速览

**有，而且生态很成熟。** 但必须先把两类东西分清——它们的攻防定位完全不同：

| 路线 | 代表 | 本质 | 能否解决 Loom 的「图像可解」短板 |
|---|---|---|---|
| **A. 拼图 / 滑块验证码** | AJ-Captcha、tianai-captcha、ArgoZhang/SliderCaptcha | 视觉挑战 + 服务端二次校验 | **不能根治**。可解性是范式问题，差别只在「破解成本」。换库只能把成本从「90 行代码」抬到「需要一点 CV 工程」 |
| **B. 纯前端组件** | vue3-slide-verify、tonrocket/slider-captcha、koncaptcha | 只做交互，校验逻辑自研 | 同上，且还要自己补服务端 |
| **C. 行为 / 无感 / PoW 验证** | **ALTCHA**、Prosopo Procaptcha、Cap、mCaptcha | 行为轨迹 + 设备指纹 + 计算难题 → 风险评分 | **能改变成本曲线**。bot 的边际成本从「一次推理」变成「按 GPU/CPU 时间计费」 |
| **D. 破解生态（威胁情报）** | awesome-captcha、ddddocr、WyheLi/behavioral-captcha | 攻击工具 | ——（用来自证 A 类方案的脆弱性） |

**三条最该记住的判断：**

1. **没有任何开源拼图库能「根治」Loom 的问题。** 拼图验证码的可解性是范式问题（缺口 = 对原图的确定性裁剪 + 半透明遮罩），换库只改变破解成本，不改变「可解」这件事。唯一能实质抬高成本的，是**随机化挑战形态**（随机形状 / 旋转 / 扭曲 / 独立加噪 / 无关遮罩）。
2. **真正改变攻防成本曲线的是无感 / PoW 路线。** 其中 **ALTCHA** 对 Loom 最友好：MIT 协议、TypeScript 前端 Web Component、**官方 Python 服务端库（`altcha-org/altcha-lib-py`，MIT）**、无 cookie / 无指纹 / 无追踪、GDPR + WCAG 2.2 AA，且仍在活跃更新（2026-10-05 当日仍有提交）。
3. **Loom 后端是 Python，这排除了大部分拼图库的「直接复用」。** AJ-Captcha 与 tianai-captcha 后端都是 **Java**，采用需引入独立 Java 服务或做移植；Python 侧没有成熟的「拼图 + 行为」一体化开源实现。

## 2. 关键结论：为什么「换一个拼图库」解决不了 Loom 的问题

1. **可解性来自范式，不是实现。** 滑块拼图的缺口永远是「从背景图裁一块 + 原位叠加半透明遮罩」。只要这个变换是**确定性**的，亮度反补偿 + 滑窗模板匹配就必然命中。AJ-Captcha、tianai-captcha、vue3-slide-verify 均属此类；差别只在于**是否额外引入随机化**。
2. **真正抬高成本的只有「随机化挑战形态」**：
   - 拼图块随机**扭曲**（distort）—— `tonrocket/slider-captcha`
   - 拼图块随机**旋转** —— `tonrocket/slider-captcha`、tianai-captcha 的旋转验证码
   - **3D / 立方体**挑战 —— `librecap/imagecaptcha`
   - 缺口用**无关遮罩**、对两者**独立加噪**
   > 上述任一都能让模板匹配失效，但都会被更强的 CV / 深度学习破解——只是把「90 行代码」抬到「一个模型」。**这是成本抬升，不是不可破解。**
3. **换语言栈的成本往往被低估。** 两个最成熟的拼图方案（AJ-Captcha、tianai-captcha）都是 Java，Loom 接入意味着**多维护一个 Java 服务**（或做 Python 移植，风险自担）。
4. **行为验证的「强」在于它不依赖视觉谜题。** Prosopo 走的是「行为 + 设备指纹 + 风险评分」；ALTCHA/Cap/mCaptcha 走的是「PoW 让 bot 按算力付费」。二者都不存在「看一眼图就能解」的问题。

| 路线 | 做法 | 改动量 | 抗自动化 | 依赖 / 运维 | 许可 | 建议 |
|---|---|---|---|---|---|---|
| **A. 自研硬化** | 在现有滑块上：拼图块随机扭曲/旋转 + 缺口改无关遮罩 + 独立加噪；权重转向「服务端时间轴 + 轨迹 `t` 校验」；保留账号锁/IP 锁为真正防线 | 小（改 `auth_captcha.py` 渲染 + 校验） | 中（挡住脚本，挡不住模型） | 无新增 | 自有 | ✅ 与 §13 建议一致，**保留滑块时的必做项** |
| **B. 引入 ALTCHA** | 以 PoW 无感验证作**主防线**；滑块降级为「风险升级时才出现的挑战」 | 中（前后端各接一个库） | **高** | 官方 Python 库，**无需新服务** | **MIT** | ✅✅ **推荐主选**：许可最友好、Python 原生、无追踪合规 |
| **C. 引入 Prosopo Procaptcha** | 自托管 provider，用真实行为分析 + 风险分级 | 大（需 Node.js provider 栈） | **最高** | 需部署 Node 服务 | Apache-2.0 | 🟡 能力最强但运维成本高；若合规要求「数据完全自持」可考虑 |
| **D. 换用 tianai-captcha** | 部署 Java 独立服务，替换现有滑块 | 中 | 中（类型多、界面好） | 需维护 Java 服务 | Apache-2.0 | 🟡 若坚持「拼图路线 + 想要成品」的折中 |
| **E. Cap (Docker REST)** | 以 PoW 作底噪层 | 中 | 高 | 需跑 Docker 容器 | Apache-2.0 | 🟡 备选（比 ALTCHA 重，但 star 更高） |

**推荐组合：B（ALTCHA 主防线）+ A（保留滑块则硬化）+ 现有「账号锁 / IP 锁 / 限流」不动。**
理由：Loom 已在 §14 确认「真正在挡暴力破解的是账号锁 + IP 锁 + 限流，而非验证码」；把验证码从「人机区分主防线」重新定位为「成本抬升层」，再用 PoW 提供无感底噪，是**改动最小、许可最干净、且实质提升**的路径。

## 6. 追问专题：双轴（2D 拖动）与「滑动 + 旋转」项目

> 追加于 2026-10-05 晚。回答「有没有用双轴的项目 / 有没有滑动+旋转的项目」。

### 6.0 先分清四种形态（命名极易混淆）

| 形态 | 定义 | 用户交互 | 服务端校验量 |
|---|---|---|---|
| 单轴滑块 | 只有 X 随机 | 横向拖条 | `x` |
| **双轴滑块** | X、Y 都参与 | 自由拖动（或拼图块 Y 随机但仍走横向拖条） | `(x, y)` |
| **旋转验证码** | 拖动条 = **角度旋钮**，拖动使图片转正 | 横向拖条，但语义是角度 | `angle`（不是 x） |
| **滑动 + 旋转双因子** | 一次交互内**既要位置对齐、又要角度对齐** | 拖到位置 + 转到角度 | `(x, y, rotation)` |

**关键区分**：「拖条转动图片」（经典旋转码）与「拖到位置 **且** 转到角度」（双因子）是两种东西，市面宣传常混用。

```go
    imageAlpha float32
    rangeDeadZoneDirections []DeadZoneDirectionType // 死区方向（左/右/上/下）
    rangeGraphSize          *option.RangeVal        // 拼图块尺寸随机
    rangeGraphAnglePos      []*option.RangeVal      // 拼图块角度随机 ← 等价「旋转」
    genGraphNumber          int                     // 缺口个数（>1 即多缺口）← 抗模板匹配
    enableGraphVerticalRandom bool                  // 垂直随机 ← 等价「双轴」
}
```

> 即：**GoCaptcha 一个 slide 模块里，双轴、多缺口、拼图块旋转三件事都有现成开关**。但它是 Go 实现。

### 6.4 对 Loom 的判断（关键）

1. **双轴几乎不抬升「图像可解」的门槛。** 我们的解题器本来就是 **2D 模板匹配**，定位缺口时天然拿到 `(x, y)`。双轴只挡住「只报一个 x 就能蒙对」的低级绕过（与 §13 修掉的 C2 `width=80` 绕过不同性质）。**对现有短板收益≈0。**
2. **拼图块「随机角度 / 随机旋转」才会实质破坏模板匹配** —— 块一转，直接滑窗的相关系数就崩。GoCaptcha 的 `rangeGraphAnglePos`、adrsch 的 `rotate` 都是这个思路。但攻击者可改用旋转不变特征或穷举角度（±30°、步长 5° 仅 13 次匹配），属**成本抬升而非不可破解**。
3. **性价比最高、且多家验证有效的是「多缺口 / 干扰缺口」**：GoCaptcha `WithGenGraphNumber(2+)`、tx_slider_captcha 的 decoy gaps、数美/易盾的多缺口。它直接攻击模板匹配的**唯一性假设**（「相关性最高峰 = 答案」），比双轴有效得多。
4. **结论**：开源里想「直接拿到双轴 + 旋转成品」—— 只有 **GoCaptcha（Go）** 较成熟，**tianai-captcha（Java）** 有纯旋转；Loom 是 Python，二者都要引入异构服务或自担风险做移植（Python 侧 `pi-captcha` **无许可证**，不能商用复用）。
   **⇒ 若仍保留滑块，正确做法是在 `auth_captcha.py` 自研硬化：多缺口 + 拼图块随机角度 + 独立加噪；而不是换库。** 与 §3 路线 A 一致。
