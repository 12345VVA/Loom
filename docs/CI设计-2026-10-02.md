## 一、总体拓扑

```
push / PR → main
│
├─ job: backend            后端 + 定时任务框架（postgres:16 service 容器）
│    ├─ ruff check / format --check
│    ├─ alembic upgrade head（迁移链验证，独立于 create_all 路径）
│    ├─ pytest 全量（TestClient 类打 PG，纯逻辑类用 sqlite 内存）
│    └─ Celery 完整性校验 ← 定时任务框架的 CI 门禁
│
├─ job: frontend           前端（无外部服务）
│    ├─ type-check（vue-tsc）
│    ├─ lint:check（不带 --fix，不改写文件）
│    ├─ vitest run
│    └─ vite build
│
└─（二期）docker-build /（三期）e2e 全栈
```

## 二、关键事实与设计决策

| # | 事实 | 设计决策 |
|---|------|----------|
| 1 | CI 上没有 `.env`，`DATABASE_URL` / `SQL_*` 全空 → [config.py:212-217](../backend/app/core/config.py) validator 直接抛 `ValueError: 数据库未配置`，任何 import app 模块的测试在收集阶段就崩 | **一期就必须挂 postgres service**，不存在"零外部服务"的过渡形态 |
| 2 | 运行配置已切 PG，但 tests/ 存在两类测试：自建 `sqlite://` 内存 engine 的（与 .env 无关）、`from main import app` 走 TestClient 的（跟随 `settings.DATABASE_URL`） | 一个 backend job 里双轨天然形成：TestClient 类测试自动打 PG service（顺便持续验证 PG 兼容），纯逻辑类继续 sqlite 内存库。**无需独立的 pg-compat job** |
| 3 | `build/cool/eps.d.ts` 不入库（`.gitignore` 的 `build/` 规则）且生成依赖后端在跑（vite-plugin 请求 `/admin/base/open/eps`）→ CI 的 type-check 必挂 | eps.d.ts / eps.json 入库（`!frontend/build/cool/eps.d.ts` 例外规则）；后续可加漂移校验 step 把"前后端 EPS 同步"变成 CI 制度 |
| 4 | `npm run lint` 带 `--fix` 会改写文件 | 用已有的 `npm run lint:check` |
| 5 | Redis 在测试中自动降级进程内缓存，conftest 已固定 3 个环境变量 | 除 postgres 外无需其他 service；Celery 校验脚本沿用 conftest 同组变量 |

## 三、Workflow 文件（`.github/workflows/ci.yml`）

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true   # 同分支新推送取消旧跑，省额度

jobs:
  backend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    services:
      postgres:                          # 与 docker-compose 注释中的版本对齐
        image: postgres:16-alpine
        env:
          POSTGRES_USER: loom
          POSTGRES_PASSWORD: loom
          POSTGRES_DB: loom_test
        ports: ['5432:5432']
        options: >-
          --health-cmd "pg_isready -U loom"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 10
    env:
      DATABASE_URL: postgresql+psycopg://loom:loom@localhost:5432/loom_test
      SECRET_ENCRYPTION_KEY: ci-test-key
      ADMIN_CAPTCHA_ENABLED: 'false'
      DEBUG: 'true'
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
          cache: pip

      - name: 安装依赖
        run: pip install -r requirements-dev.txt

      - name: Ruff 检查
        run: |
          ruff check .
          ruff format --check .

      - name: Alembic 迁移链验证（16 个版本逐一应用）
        run: alembic upgrade head

      - name: 后端测试（TestClient 类打 PG，纯逻辑类用 sqlite 内存）
        run: python -m pytest

      - name: Celery 任务注册与调度完整性校验
        run: |
          python - <<'EOF'
          from app.celery_app import celery_app

          tasks = celery_app.tasks

          # 1. 显式路由引用的任务必须已注册
          for name in celery_app.conf.task_routes or {}:
              assert name in tasks, f"task_routes 引用了未注册任务: {name}"

          # 2. Beat 调度条目引用的任务必须已注册
          for entry_name, entry in (celery_app.conf.beat_schedule or {}).items():
              task_name = entry.get('task') if isinstance(entry, dict) else entry.task
              assert task_name in tasks, (
                  f"beat_schedule[{entry_name}] 引用了未注册任务: {task_name}"
              )

          registered = {n for n in tasks if not n.startswith('celery.')}
          print(f"OK: {len(registered)} 个任务注册，调度与路由引用有效")
          EOF

  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: npm
          cache-dependency-path: frontend/package-lock.json

      - name: 安装依赖
        run: npm ci

      - name: 类型检查
        run: npm run type-check      # 前提：eps.d.ts 已入库（决策 3）

      - name: ESLint 检查（不改写）
        run: npm run lint:check

      - name: 单元测试
        run: npm run test:unit

      - name: 生产构建
        run: npm run build
```

## 五、定时任务框架的 CI 保障口径

Celery/Beat 在 CI 里不"真跑调度"，卡住三类回归（已并入 backend job 末尾 step）：

1. **任务注册完整性**——`import celery_app` 后 autodiscover 的任何任务模块 import 错误直接失败（本地常见事故：改模块名导致 worker 起不来，CI 提前拦截）；
2. **Beat schedule 引用一致性**——`beat_schedule` 条目引用的任务名必须真实注册（防止调度已改名/删除的任务而静默失败）；
3. **task_routes 队列一致性**——显式路由表引用的任务必须有效。

task 模块（DB 驱动动态调度、反射执行）的业务语义由既有 pytest 覆盖；真实 Redis + worker + Beat tick 的端到端冒烟不进常规流水线，留给三期 e2e。

## 六、三步走：CI 推动 SQLite 退场

### Step 1（一期，本设计）

双轨并存：TestClient 类测试打 PG service、纯逻辑类 sqlite 内存。CI 从第一天守 PG 兼容性。

### Step 2（二期）：测试参数化收编

`conftest.py` 提供统一入口，逐文件替换 65 个文件里的硬编码 `create_engine("sqlite://", ...)`：

```python
def make_test_engine():
    """测试 engine 工厂：优先 TEST_DATABASE_URL，缺省 sqlite 内存库。"""
    url = os.environ.get("TEST_DATABASE_URL")
    if url:
        return create_engine(url, pool_pre_ping=True)
    return create_engine(
        "sqlite://",
        connect_args={"check_same_thread": False},
        poolclass=StaticPool,
    )
```

纯机械替换，按模块分批，每批 CI 验证。

### Step 3（三期）：主 job 切 PG 全量 + SQLite 代码退场

主 backend job 的 pytest 全量走 PG；一次性完成退场收尾（即评审 P2-a 的收敛动作）：

| 收尾项 | 位置 |
|---|---|
| 删除 `_ensure_sqlite_compatible_schema` 190 行补列字典 | `app/core/database.py:145-395` |
| 删除 sqlite 路径标准化等分支辅助 | `app/core/database.py:39-83` |
| checkpointer 的 sqlite 后端移除或标记 legacy | workflow 模块 `checkpointer.py` |
| compose 解注释 postgres、backend 依赖它 | `docker-compose.yml:18` |
| `.env.example` 默认值翻转为 PG | `backend/.env.example:11` |
| conftest 防护的 sqlite 兜底分支移除 | `tests/conftest.py` |
| 全仓 grep `sqlite` 清零（testsession 专属除外） | 收尾验证 |

## 七、上线首跑预期管理

一期首次全量跑**大概率会红**，属正常（CI 把隐性债变显性）：

- eslint 对 800+ 处 `any` 的告警——真问题修掉；纯告警类用 `--max-warnings` 阈值过渡；
- 历史记录过的测试隔离问题在 PG service 上现形——逐个修复即是在还 Step 2 的债；
- `ruff format --check` 若从未统一跑过格式，首次会大面积红——单独提交一次纯格式化 commit 解决。
