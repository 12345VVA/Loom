## 5. 根因分析：为什么单缺口模式下「定位即破解」

### 5.1 缺口的三个结构特征，每一个都是可被阈值分割的
| 特征 | 来源 | 攻击者视角 |
|---|---|---|
| **色度**：洞是图中唯一非灰区域 | `tint_alpha=150` + `sat=0.95`，而背景**三通道同值真灰**（`_random_bg_color`） | `S > 70` 一步二值化 |
| **亮度**：洞内均值 = `0.57 × 局部背景` | `_HOLE_DARK_ALPHA=110` → `_hole_noise_mean` | 44×44 滑窗均值 argmin |
| **形状**：洞与拼图块共形 | 单实例 `hole_mask`（**这是修复 S6 的正确做法**） | 但单缺口下形状不再承担判别 |

洞内噪声 `σ=25` 只破坏**内容相关性**（这正是 `S1` 归零的原因），对**位置定位毫无影响**——1936 个像素平均后噪声标准差降至 `25/44 ≈ 0.57`，43% 的系统性灰度落差完好保留。

### 5.2 逻辑上的根本问题
被测方在代码注释中反复表述「**定位缺口本就不是安全边界**」（`auth_captcha_render.py:35,393-395`）。

这个论断在**多缺口模式**下是成立的：定位之后还有「从 k 个同形状候选里选出真缺口」这一步，而这一步的判别依据是「拼图块↔缺口的色调相等」——机器需要额外的匹配器。

但在**单缺口模式**下，`k=1`，**「选」这一步被删除了**。于是：
```
攻击者需要的全部信息 = 缺口在哪
                     = 唯一那个非灰 / 更暗的矩形
校验逻辑需要的全部信息 = 滑块的 x 是否落在 target_x ± 12（captcha_check 只比 x）
```
两者**完全重合**。「定位非安全边界」的论证前提（存在定位相同但真假不同的候选）在该模式下已不存在，因此该论证**不能从多缺口模式迁移过来**。

### 5.3 「描边移除」并没有消除信标
`_random_bg_color` 的注释已修正为「压暗背景与缺口可定位性无关」。但移除描边同时**降低**了背景的结构化噪声（代码里残留的 60 条随机线颜色域与背景同为 100-160），使「唯一暗块」的显著性进一步提升。实测 A3（纯亮度）在多缺口模式下 64.2%，在单缺口模式下 85–92%。

## 6. 方法论：「1/k 随机下界」的口径问题

被测方在两轮报告中均以 `随机下界 = 1/k` 作为达标线，理由是「任何策略不优于盲猜才算过关」。这在**多缺口模式**下是合理的（`k≈2.5`，下界 ≈41%）。但在单缺口模式下：

```
k = 1  →  1/k = 100%  →  「任何策略都不优于 100%」自动成立
```

**这个下界把「定位」这一步的收益记作了 100%，即假设攻击者已经免费完成了最难的一步。**

正确的盲猜定义应当是：**不做任何图像分析**，直接在滑块行程内猜 x：

```
P(命中) = (2 × 12 + 1) / (256 + 1) = 25/257 ≈ 9.7%
```

| 口径 | 单缺口模式下的值 | 问题 |
|---|---|---|
| `1/k`（被测方） | 100.0% | 隐含「已定位」，恒真、不可否证 |
| 真实盲猜（本次） | **9.7%** | 衡量「完全不看图」的基线 |

**建议**：单缺口模式下应禁用 `1/k` 口径，改用「真实盲猜下界」；并在基准中**固定加入定位策略（A1/A2/A3）**，否则「只测自家求解器」的结构性误判会再次出现（这正是上一轮报告 §教训 的内容）。

## 7. 建议（按优先级）

### P0｜明确单缺口模式的定位
单缺口模式下验证码**不提供任何抗自动化能力**（端到端 100%）。建议二选一：

**(a) 恢复多缺口（`DECOY ≥ 1`）并接受既知代价**
- 多缺口是**唯一**让「定位 ≠ 答案」的机制。
- 代价：被测方已在 `5a7d074` 中实测「色调拉满 → S1 复活 100%」。即：**在多缺口模式下，任何足以让人类完成「拼图块↔缺口」匹配的色调强度，都同样足以让机器完成。**
- 结论：这不是参数调优问题，而是**滑块拼图范式的天花板**。

**(b) 放弃「图像任务」作为防线，把验证码降级为 UX 减速带**（现有代码注释事实上已持此立场）
若采用此定位，建议：
1. **删除「抗解」相关宣称**，避免给后续验收和各方预期造成误导；
2. 把资源集中到**真正生效的防线**：账号锁、IP 锁、限流、设备指纹、风控评分；
3. 若确需抗自动化，改为**不依赖视觉判别**的机制（工作量证明类，如 ALTCHA；或二次因子）。参见 `docs/开源行为验证与拼图验证码调研-2026-10-05.md`。

### P1｜基准红线（防复发）
- 基准脚本**必须**包含定位策略（色度连通块 / 色度滑窗 / 亮度滑窗），不得只测内容匹配（S1）。
- 单缺口模式下**不得**使用 `1/k` 作为随机下界。
- 新增「输出级防回归」应包含：**同一张图在 `tint_alpha=0` 时仍能被 A3 定位**（当前 85–92%，若未来想靠"去色调"提升安全性，此断言会失败）。

### P2｜仍然存在、但已被正确修复的项（本轮复核通过）
- 形状零信号（`hole_mask` 单实例）✅
- 明度与真假解绑（`rng.shuffle`）✅
- 伪缺口同行（`layout_decoys` y = `target_y`）✅
- 前端 `isTrusted` 未校验 —— 合成事件可用（前端零改动是硬约束，属**已知取舍**，但应记入风险台账）

## 附录：关于「每次都要点允许」（Chrome 远程调试授权弹窗）

**现象**：每次执行浏览器命令都提示 `browser-harness: Chrome is asking "Allow remote debugging?" — click Allow to continue.`

**根因**：不是 browser-use 的问题，而是 **Chrome M144 的安全策略**——当外部进程通过 CDP 附加到**已经在运行的 Chrome** 时，Chrome 会要求按「实例」授权一次。`browser_harness/daemon.py:341` 与 `admin.py:701` 对此有明确说明。

**三种解法**：

1. **一次授权，长期生效（推荐）**
   在弹窗上**勾选**「Allow remote debugging for this browser instance」**再**点 Allow。Chrome 会为该浏览器实例记住该选择，之后不再询问。

2. **用专用的自动化 Chrome（彻底隔离）**
   `daemon.py:287` 给出的推荐做法：
   ```
   chrome.exe --remote-debugging-port=9222 --user-data-dir=<专用目录>
   ```
   独立的 `user-data-dir` 不触发该确认框。之后用 `BU_CDP_URL=http://127.0.0.1:9222` 让 browser-use 连接。

3. **绕开 CDP（本次采用）**
   本次端到端**全部改用纯 JS 合成事件**，不调用 `Input.dispatchMouseEvent`，因此不受该弹窗影响。该方法的前提是被测页面前端不校验 `isTrusted`（Loom 当前如此）。

**附注**：另一类「允许」弹窗来自命令执行权限确认（每次 Bash 调用需批准）。本次已通过**合并命令**大幅减少调用次数；如需进一步免确认，可在设置中把 `browser-use` 等命令加入允许规则。
