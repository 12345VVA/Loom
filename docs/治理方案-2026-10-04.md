## 二、分批设计

### G1 供应链与 CI 加固（H1、M1）

1. **新增 `.github/dependabot.yml`**：三个 ecosystem——`pip`（directory `/backend`）、`npm`（directory `/frontend`）、`github-actions`（directory `/`）；`schedule.interval: weekly`、`open-pull-requests-limit: 5`。
   - 注意点写进配置注释：pip 依赖升级 PR 会与手维护的 `requirements.lock` 冲突——PR 若红，在**同一 PR** 补提交 lock 再生，流程即"下限提升 → lock 强制对齐"。
2. **CI 增加审计 step**：
   - backend job：`pip-audit`（requirements-dev 安装后对实际环境审计，或 `-r requirements.txt`）；
   - frontend job：`npm audit --audit-level=high`。
   - **门禁策略（决策点 D2）**：起步 `continue-on-error: true` 只报告不阻断，输出摘要进日志；清完存量高危后翻转为硬门禁。
3. **CI 加超时（M1）**：backend job `timeout-minutes: 30`、frontend job `timeout-minutes: 20`（当前全量远低于此值，纯兜底）。

**验收**：dependabot 首轮 PR 出现；审计 step 有基线输出；CI 挂死场景可被超时截断。

### G4 workflow↔workflow_eval 解耦 + 守卫全量化（H4）★核心批

**定向原则**：workflow_eval（评测）与 workflow_annotation（标注）是 workflow 的"质量消费域"，依赖方向**单向**：`annotation → eval → workflow`。禁止任何 workflow → eval/annotation 的边。

**现状边清单**：

| 边 | 位置 | 性质 |
|---|---|---|
| eval → workflow（合法） | `eval_run_service.py:17-18`、`eval_orchestrator.py:20` | 静态模型/服务依赖 |
| eval → workflow（合法但脏） | `eval_tasks.py:24` 引私有符号 `_async_execute` | 需公共化 |
| annotation → eval（合法但脏） | `annotation_service.py:15-16` 引私有符号 `_assert_run_owned` | 需公共化 |
| **workflow → eval（违规）** | `cleanup_service.py:141` lazy 引 `WorkflowEvalCaseResult`（实例删除时级联清评测产物） | **待斩断** |
| **workflow → eval（违规）** | `llm_judge.py:126` lazy 引 `workflow_service.run_ai_chat`（评测裁判调用 LLM） | **待斩断** |

**解耦四步**：

1. **cleanup 反转为 eval 自治**：workflow 实例删除时的评测产物级联清理，改为 eval 模块自治——`eval_tasks` 增加孤儿清扫（按 `workflow_instance_id` 反查已不存在实例的 eval 产物删除，挂入既有 Beat 调度）。选孤儿清扫而非外键 CASCADE：对存量数据安全、迁移面小。删除 `cleanup_service.py:141` 的 import。
2. **llm_judge 依赖下沉（实现期二选一）**：
   - 核实 `workflow_service.run_ai_chat` 是否仅为 ai runtime 的薄封装；若是，judge 直连 ai 模块运行时（ai 是公共底座，`eval → ai` 本就是合法方向）；
   - 若含 workflow 特有逻辑，则在 eval 侧定义 `JudgeChatPort` 协议，由 orchestrator 装配时注入实现（依赖倒置，方向仍单向）。
3. **私有符号公共化**：workflow 侧新增公共执行入口（如 `workflow/service/execution_api.py` 暴露 `execute_async`，docstring 标注"跨模块契约"）；eval 侧 `_assert_run_owned` 移至 eval service 公共层。
4. **守卫升级（在 1-3 完成后执行，设计已按 G2 诊断结果修正）**：G2 全量诊断（`scripts/verify_arch_cycle.py`）实测——顶层口径 640 边 0 环；全量口径 704 边 **3 个环，全部为模块内部环**（workflow 6 文件、base 4 文件、task 2 文件，均为 B4 拆分后兄弟文件间的 lazy 互引）；workflow↔eval 是**方向违规而非导入环**（eval→workflow 指向 model 层，未回流成 SCC）。据此守卫升级为两条：
   - **模块作用域 SCC**：SCC 输入切全量 AST，但仅"跨模块/跨层的 SCC"判失败（环内模块分属不同 `app.modules.{name}` 或分属 framework/core/modules 层即红）；同模块内部的 lazy 互引是拆分后的合法形态，容忍。
   - **方向守卫**：新增轻量检查——`app/modules/workflow` 源码 0 处 `workflow_eval`/`workflow_annotation` 引用（grep 或 AST 边策略），堵"eval→workflow 指向 model 层不回流"这类不成环的方向违规。

**验收**：全量 AST SCC 守卫绿；加一条轻量 grep 守卫：`app/modules/workflow` 源码 0 处 `workflow_eval`/`workflow_annotation` 字样；`eval_tasks` 孤儿清扫有单测。

## 四、风险与顺序依赖

1. **G4 守卫切换必须在解耦落地之后**——否则切换日 CI 常红。G2 诊断先行是硬前置。
