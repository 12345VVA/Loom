## 2. 本轮新发现：R2 账号锁 DoS（P0）

### 2.1 因果链

```
① 验证码可解（A1/A2 = 100%，本轮与上轮独立复现）
   ↓
② 解出的票通过 captcha_check → 请求推进到【凭证校验】
   ↓
③ 错密码分支  self._mark_login_failure(payload.username, login_ip)
   auth_login.py:95-101 —— count_account 默认 True
   ↓
④ 账号维度计数 +1；计满 BASE_LOGIN_ACCOUNT_FAIL_MAX=5
   → 写 login:lock:account:{任意用户名}   （auth_login.py:324-344）
   ↓
⑤ 该账号的【正确凭证】随后被拒：
   _check_login_risk（auth_login.py:317-322）位于 login 最前、captcha_check 之前
   → 429 「账号已被临时锁定，请稍后再试」
```

### 2.2 对照实验（单变量：验证码是否被攻破）

```
=== A 对照组：垃圾验证码 + 错密码 ×5（H2 修复应拦截账号计数） ===
  A1: 401 '验证码不正确或已失效' | account_cnt=None ip_cnt=1
  A2: 401 '验证码不正确或已失效' | account_cnt=None ip_cnt=2
  A3: 401 '验证码不正确或已失效' | account_cnt=None ip_cnt=3
  A4: 401 '验证码不正确或已失效' | account_cnt=None ip_cnt=4
  A5: 401 '验证码不正确或已失效' | account_cnt=None ip_cnt=5
  → 对照结论: account_counter=None lock=None

=== B 攻击组：已解验证码 + 错密码 ×5 ===
  B1: capId=ab2ca167c2 解x=21  -> 401 '用户名或密码错误' | account_cnt=1 ip_cnt=6
  B2: capId=8d40bbe6f9 解x=13  -> 401 '用户名或密码错误' | account_cnt=2 ip_cnt=7
  B3: capId=2a69ca51af 解x=130 -> 401 '用户名或密码错误' | account_cnt=3 ip_cnt=8
  B4: capId=885ddeee7d 解x=27  -> 401 '用户名或密码错误' | account_cnt=4 ip_cnt=9
  B5: capId=62aa4da298 解x=68  -> 401 '用户名或密码错误' | account_cnt=5 ip_cnt=10
  → 攻击结论: account_counter=5 lock=1 总尝试 5 次（验证码过 5/5）耗时 2.1s

=== C 影响：admin 的【正确密码】+ 已解票（合法用户应被拒） ===
  C: 429 '账号已被临时锁定，请稍后再试'

=== D 恢复：清理锁定计数后合法登录 ===
  D: 200 'success' code=1000
```

| 阶段 | 账号计数 | 锁 | 合法凭证结果 |
|---|---|---|---|
| A 对照（垃圾票 ×5） | **0（未增长）** | 无 | — |
| B 攻击（已解票 ×5） | 0 → **5** | **置位** | — |
| C 影响（正确密码） | — | 置位中 | **429 拒绝** |
| D 清理锁定键 | 0 | 清除 | **200 通过** |

### 2.3 关键：这不是「本就存在」的问题

**A 组证明：验证码拦得住时，账号维度计数根本不增长**（这正是 H2 修复的设计目的）。A 与 B 的**唯一差异**是「验证码是否被攻破」，其余请求参数、账号、IP、密码全部相同。

> **∴ 该 DoS 是「验证码失效」的直接后果，而非 H2 的遗漏。H2 修复本身是有效的 —— 它只是把门锁交给了一个已经失效的守卫。**

### 2.4 攻击成本 vs 全部防线（数值）

以「永久维持某账号锁定」为目标：

| 防线 | 阈值 | 攻击实际占用 | 是否触发 |
|---|---|---|---|
| 中间件限流 `/admin/base/open`（按 path 分桶） | 30/min | 6 请求 / 900s = 0.4 req/min | ❌ **1.3%** |
| 验证码签发限流 `captcha:issue:{ip}` | 100 / 300s | 5 / 300s | ❌ **5%** |
| IP 失败锁 `login:lock:ip:{ip}` | 20 / 900s | 5 / 900s（与账号锁同窗口） | ❌ **永不触发** |
| 账号锁 `login:lock:account:{user}` | 5 / 900s | 恰好 5 / 900s | ✅ **攻击者要的就是它** |
| 登录日志 | — | `risk_hit` 仅在第 5 次置 1，落 5 行/15min | ⚠️ 仅留痕，**无告警/异常检测**（全仓库核实：`risk_hit` 只被登录日志查询接口消费）|

**关键结构性事实**：`ACCOUNT_FAIL_MAX(5) < IP_FAIL_MAX(20)` 且两者**同窗口（900s）**，所以「维持账号锁」所需的行为**永远够不到 IP 锁阈值**。IP 维度的兜底在数学上被架空。

维持成本：**5 次 / 15 分钟 = 0.33 次/分钟**（对上限的 1.1%）。

### 2.5 无自救路径

全仓库检索（排除测试）后确认：**不存在任何解锁接口**。

```

（仅 auth_login.py 内部命中）
```

`_clear_login_failure` 只在**登录成功**时调用（`auth_login.py:164`），而锁定恰好使登录不可达 → **账号 15 分钟内无法自救，也无管理员清锁接口**，唯一出路是等 TTL 到期（或直接改 Redis）。

## 3. 残防守线其余两项：核实通过

`64fb3c8` 把抗自动化能力寄望于「失败锁定 / 限流 / 一次性票据」。三条逐条实测：

```
[T1] 首次 401 '用户名或密码错误' / 重放 401 '验证码不正确或已失效' → 票据一次性消费生效
[T2] 首次 200 'success'        / 重放 401 '验证码不正确或已失效' → 成功路径同样一次性消费
[T3] 4 路并发 → 越过验证码 1 路 → GETDEL 原子消费成立（无双花）
```

- **一次性票据**：`cache_get_del`（GETDEL）在 `captcha_check` 最前消费，错密码路径与成功路径都被正确回收；4 路并发只有 1 路越过。✅
- **IP 绑定 / XFF 防线**：`get_client_ip` 仅在 `TRUSTED_PROXIES` 非空**且**直连对端本身属于可信代理时才读 `X-Forwarded-For`；本环境 `TRUSTED_PROXIES=""` → 一律取 socket 对端 IP。**无法伪造 IP 绕过 IP 锁或限流。** ✅（代码核实）
- **失败锁定**：❌ 见 §2。

**结论：三条防线里两条扎实、一条自身即武器。而唯一扎实的两条都无法阻止 §2 的攻击。**

## 4. 框架层面：口径校准留下的自洽性缺口

`64fb3c8` 的终态口径是：

> 验证码 = UX 减速带；抗自动化防线 = 失败锁定 / 限流 / 一次性票据。

这个口径有个未闭合的地方：

- **若验证码真的不提供抗自动化能力**（A1/A2=100%），那么账号锁就从「抗爆破机制」退化为「**免费 DoS 武器**」——因为攻击者能无条件越过前置校验、以 5 次请求锁死任意账号，而**唯一能阻止这件事的机制（H2）恰好依赖验证码拦得住**。
- **反过来**：H2 修复之所以成立，**恰恰因为**验证码把未经攻破的攻击者挡在凭证校验之外。这是「验证码是安全边界」的证明。
- **所以**：验证码不是一个可以被「不算边界」的组件。它是**账号锁计数器的门**。它的失效不是把账号锁削弱一点，而是**把账号锁的语义从"保护"翻转成"武器"**。

**定量佐证**：账号锁把单账号爆破成本从「30 次/min/IP ≈ 43200 次/天」压到「480 次/天」，约 **90×**。这个价值真实存在 —— 所以**修复方向不是删锁，而是让锁不可被无条件触发**。

## 5. 修复建议（按性价比排序）

| 优先级 | 措施 | 代价 | 效果 |
|---|---|---|---|
| **P0-1** | 账号锁改为 **(account, IP) 复合维度**：仅当同一 (账号,IP) 组合累计失败达标才计账号维度；纯账号维度只降级为**告警**不硬锁 | 小（改 key 构造 + 判定） | 攻击者只锁死自己；分布式爆破仍有告警兜底 |
| **P0-2** | 硬锁 → **渐进延迟**：第 n 次失败施加 `min(2^(n-1), 30)s` 延迟（或要求递增的验证码难度） | 中 | 抬高爆破成本至与硬锁同量级，但**不产生"合法用户被拒"的可用性悬崖** |
| **P0-3** | **自助解锁**：账号锁命中时，向账号所有者下发带外验证（邮件/短信/2FA），验证通过即清锁 | 中（需通知通道） | 把无解 DoS 变成可恢复事件 |
| **P0-4** | **告警**：`login:fail:account:*` 在窗口内跨阈值时推送告警（当前 `risk_hit` 只落库不告警） | 极小 | 让 §2 的攻击可见；攻击者 5 行/15min 的成本是可控的诱饵 |
| **P1-1** | 提高 `BASE_LOGIN_IP_FAIL_MAX` 与账号锁的**不对称性**：让账号维度失败必须先消耗 IP 维度（例如账号计数仅在 IP 计数 ≥ 某值时累加），使 IP 兜底不再被数学架空 | 小 | 直接封死「5 次即锁」的廉价路径 |
| **P1-2** | 把 A1/A2/A3 定位策略固化为**发布前红线**（本轮已进 bench，但未进 CI 门禁） | 小 | 防「基准只测自家求解器」重演 |
| **不建议** | 直接删除账号锁 | — | 爆破成本回升 90×，得不偿失 |

## 7. 本轮操作与坑（供复现）

- **环境复原**：测试前清理了 `ratelimit:*` 与 `login:fail:ip:127.0.0.1`（上轮残留）；测试后**已删除全部 `login:*` 与 `ratelimit:*` 键**，`admin` 恢复正常可用（与 §D 阶段一致）。**未改动任何被测代码，未留下锁定状态。**
- **求解器合并规则**：多数票（vote）不是好的合并器 —— 上轮第四轮 A1=214 / A2=208 / A3=131 三者互不重合时，按「最大票数、平票取最小 x」的规则恰好选中了离群的 A3，导致该轮被验证码拦下。**正解是「±tol 容差聚类 + 优先 A1」**（A1 单策略实测 100%）。
- **攻击脚本必须循环到真正锁定**：单次求解失误会漏判，固定的 5 轮循环会得出「未锁定」的错误结论。
- **`browser-use` 3.0 的 `js()` 执行世界在表达式返回后即回收**（`setTimeout` 不再触发）→ 多步拖动必须 busy-wait 全同步（沿用上轮结论）。
- **Chrome「Allow remote debugging?」**：本次仍出现，但不影响执行。彻底免除的三种方式见上轮结论：弹窗勾选记住 / 专用 `--user-data-dir` profile / 全走纯 JS 合成事件（本次采用）。
- **`MiniRedis`**：Anaconda 无 `redis` 包，本机也没有 redis-cli；直接用 40 行 RESP 协议实现即可完成 GET/DEL/SCAN，避免引入依赖。

## 8. 与前两轮的关系

| 轮次 | 对象 | 核心结论 |
|---|---|---|
| 一 | `5ce70ee` | 加固对自家求解器有效（100%→20.8%），但四条旁路 96.7–100% |
| 二 | `98a8531`/`5a7d074` | 单缺口模式把「三选一」变成「定位唯一目标」，独立定位器 100% |
| **三** | **`64fb3c8`** | **宣称全部核实通过；口径校准到位。但正式采纳的「抗自动化防线=失败锁定」自身即 DoS 武器：5 次/2.1s 锁死任意账号，且全程不触碰任何限流阈值、无解锁接口、无告警。** |

**三轮共同的方法论主线**：验证码/账号锁的强度只能由「与被测机制正交的通道」来测量。第一轮测错了对象（自家求解器），第二轮测错了范围（只看判别不看定位），**第三轮测错了层次（只测验证码，没测「接管其职责的防线」）**。
