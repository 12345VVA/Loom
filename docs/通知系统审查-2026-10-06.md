## 一、结论

**TL;DR —— 分层与权限骨架是干净的，问题集中在「事务边界」和「文档承诺大于实现」。无 CRITICAL，3 项 HIGH 都是「静默出错」，不是「可被攻击」。**

> **成熟度自评：5.5 / 10**（骨架 8，正确性 4）。扣分点：投递非原子（-1.5）、软删除不传导（-1.0）、静默失败无回执（-0.8）、两处死特性 `notification_rule`/`scheduled_at`（-0.6）、错误处理与测试覆盖缺口（-0.6）。加分点：权限接线完整、分层清晰、模板与受众抽象可复用。

| 维度    | 评价      | 说明                                                                                       |
| ----- | ------- | ---------------------------------------------------------------------------------------- |
| 访问控制  | ✅ 良好    | 全部接口在 `admin` scope，经 `authorize_admin_request` 校验；跨用户读取被数据层 `user_id` 过滤挡住（已确证不成立跨用户泄漏） |
| 事务正确性 | ❌ 弱     | 投递非原子，会产生「0 收件人的孤儿消息」（已实证）                                                               |
| 状态一致性 | ❌ 弱     | 软删除不向用户侧传导；未读数与列表过期口径不一致                                                                 |
| 功能完整度 | ⚠️ 有死代码 | `notification_rule` 零消费方；`scheduled_at` 无调度器；无投递渠道抽象                                     |
| 错误处理  | ⚠️ 弱    | 4 处未捕获异常会 500 或污染任务状态；空受众静默成功                                                            |
| 测试覆盖  | ❌ 不足    | 9 个用例全部覆盖 happy path，无一条覆盖过期/软删除/事务回滚/越权撤回                                               |
| 文档一致性 | ⚠️ 有偏差  | 框架说明缺 5 个已实现接口，且对角色范围和 `notification_rule` 的描述与代码不符                                      |

**判级口径**：所有接口均需 admin 级权限，故本报告**不设 CRITICAL**。HIGH 保留给「正常运维就会发生、且静默失败/污染数据」的缺陷。

## 七、能力缺口（非缺陷，属产品决策）

1. **无投递渠道抽象**：只有站内信。邮件 / 短信 / Webhook / 企业微信需在服务层加 provider —— 现有 `_send` 是唯一出口，扩展成本低（架构上留有空间）。
2. **无实时推送**：顶栏 60s 轮询（`toolbar-notice.vue:180-183`），而平台已有 Redis SSE 基础设施（工作流实例状态推送在用）→ 可复用，降低轮询成本、提升时效。
3. **通知出口不对称**：只覆盖工作流**失败**，无成功 / 人工介入 / 被拒绝；治理告警走 `send_business` 手拼标题，未用模板。
4. **无已读回执批量导出**：`recipients` 只能按单条消息查，无「按人/按时间段」统计。
5. **无用户级偏好**：不能按 `message_type` 订阅/退订，只能靠归档。

**唯一实质分歧**：外部把「写扩散 N+1」定为**高危**，本文档定为 MEDIUM（M10）。裁决依据：
1. 全平台**无「全员」选项**，`all_admins` 实取超管（量级很小），大受众仅经部门/角色可达；
2. 更关键 —— `_send` 路径下 message 为**全新行**，`_insert_recipients` 中的 `exists` 查重**在功能上冗余**（不可能命中），故正确做法是**直接删除该查询**而非仅做批量优化；
3. 综合，其真实影响是"可优化的浪费"而非"线上不可用"。

故维持 MEDIUM，但**采纳**其唯一索引与批量写入方案。
